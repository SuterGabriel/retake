# 0003: Enums as text with CHECK constraints, ids as uuid4

## Status
Accepted (2026-09-17)

## Context and problem
The first migration fixes two choices that are painful to change later: how enum-like columns
(`takes.status`, `findings.type`, `findings.status`, `ledger_entries.kind`) are stored, and what
primary keys look like. Finding types are expected to grow (click detection is in the parking
lot), and ids appear in URLs and SSE events.

## Decision drivers
- Adding an enum value must be a routine migration, visible to Alembic autogenerate
- Ids must be safe to expose and available before the row exists (jobs, idempotency keys)
- Keep the schema explainable in `\d table`

## Considered options
- Enums: native Postgres `ENUM` type vs. `VARCHAR` + `CHECK` constraint
- Ids: `uuid4` generated in Python vs. `serial`/`identity` integers

## Decision
**Text + CHECK** (`sa.Enum(native_enum=False, create_constraint=True)`): a new value is a
constraint replace that autogenerate detects; a native `ENUM` needs a hand-written
`ALTER TYPE ... ADD VALUE` and an explicit `DROP TYPE` on downgrade.
**uuid4 in Python** (`default=uuid.uuid4`): not guessable, known before `INSERT`, so the worker
can build `f"{kind}:{segment_id}:{version}:{attempt}"` without a round trip.

## Consequences
- Good: enum changes and downgrades are ordinary migrations.
- Good: ids can go into events and URLs without an exposure concern.
- Bad: uuids are 16 bytes and not insertion-ordered; `created_at` indexes carry ordering.
- Bad: CHECK constraints do not show up as a type in `\d`, only under "Check constraints".

## Confirmation
`tests/test_db_invariants.py` exercises the constraints against the real database; the
migration's downgrade drops everything without leftover types (`alembic downgrade -1` is clean).

## Interview explanation
I store enums as text with a CHECK constraint because adding a value then stays an ordinary,
autogenerated migration, unlike a Postgres ENUM type. Ids are uuid4 generated in Python so the
worker can compute idempotency keys before inserting and ids are safe in URLs. Both choices
trade a little storage for migrations and code that are easy to explain.
